# 고도화 전략

이 문서는 현재 `output/presentation.html`을 프로토타입으로 보고, 최종 발표 품질로 끌어올리기 위한 작업 기준이다. 실제 슬라이드 구조 변경이 필요하면 먼저 커밋 상태를 확인한 뒤 `input/09_final-slide-map.md`를 수정한다.

## 현재 상태 진단

- 현재 덱은 31장 구성으로 실행 가능한 HTML 발표자료이며, 주요 이미지와 다이어그램 리소스가 연결되어 있다.
- dev 브랜치 코드 기준으로 `sensor_data`의 단일 `id` primary key, callback 저장, WebSocket 갱신, 비동기 분석 흐름 등 핵심 기술 주장은 1차 정정되어 있다.
- 다만 현재 결과물은 프로토타입 성격이 강하다. 일부 화면은 원본 리소스를 삽입한 수준이고, 다이어그램/스크린샷의 주석, 출처, 강조점이 발표 흐름에 완전히 녹아 있지 않다.
- `09_final-slide-map.md`는 구조 기준으로는 유효하지만, 고도화 단계에서는 "발표에서 보여줄 장면"과 "코드 근거"를 더 명확히 연결해야 한다.

## 고도화 목표

1. 발표 시나리오를 "기능 나열"에서 "문제 인식 - 판단 구조 - 구현 근거 - 시연 가능 범위"로 강화한다.
2. 모든 기술 주장을 dev 브랜치 코드, 제공 자료, 생성 리소스 중 하나의 근거와 연결한다.
3. 현재 구현 범위와 향후 확장 범위를 명확히 분리한다.
4. Style A의 시각 언어를 유지하되, 각 슬라이드가 하나의 장면처럼 보이도록 이미지, 다이어그램, 텍스트 밀도를 다시 조정한다.
5. 발표용 한국어 문장을 더 짧고 명확하게 다듬고, 기술명은 필요한 경우에만 English로 둔다.

## 핵심 개선 축

### 1. 시나리오 고도화

- 인트로는 프로젝트 정의, 팀 역할, 전체 구조를 빠르게 보여주는 방향으로 유지한다.
- 개발 필요성 파트는 빗물받이 문제를 과장하지 않고, "강우 중 상태 변화에 빠르게 대응하기 어렵다"는 관찰 문제로 정리한다.
- 벤치마킹은 디자인 모방이 아니라 시나리오 비교로만 사용한다.
- AI 파트는 YOLO, OpenCV, XGBoost를 각각 따로 설명하기보다 "이미지 근거 + 센서 근거 + 최종 분류"의 판단 흐름으로 연결한다.
- 웹/서버 파트는 DB/ERD를 먼저 보여준 뒤 callback, WebSocket, 화면 반영을 설명한다.
- 인프라 파트는 운영 완료 주장이 아니라 배포 구성과 운영 시 확인해야 할 항목 중심으로 정리한다.
- 마무리는 기대효과보다 "현재 시연 가능한 흐름"과 "확장 시 필요한 다음 단계"를 분명히 보여준다.

### 2. 근거 관리

- `sensor_data`는 composite primary key가 아니라 단일 `id` primary key로 설명한다.
- `risk_score`는 실제 침수 확률이나 물리적 홍수 위험 점수가 아니라, 내부 위험도 분류를 위한 계산 점수로만 설명한다.
- real-time CCTV, real IoT sensor, MQTT 연동은 현재 구현이 아니라 향후 확장으로 둔다.
- scheduler는 구현 코드와 실행 설정을 구분해서 설명한다. 운영 가정에서는 주기 실행 가능성으로 말하되, 현재 실행 완료처럼 단정하지 않는다.
- WebSocket은 화면 데이터를 직접 들고 오는 통로가 아니라, 화면 갱신을 유도하는 trigger로 설명한다.

### 3. 리소스 고도화

- 실제 화면 캡처는 dashboard, detail, ERD, architecture, sequence처럼 발표 근거가 되는 장면에 우선 배치한다.
- 원본 리소스에 이전 프로젝트명이나 불필요한 제목이 보이면 crop 또는 재작성한다.
- 저해상도 다이어그램은 HTML/SVG 기반으로 다시 그리는 것을 우선한다.
- 확보하지 못한 사진형 리소스는 임시 생성 이미지를 사용할 수 있으나, 실제 구현 근거로 오해되지 않게 캡션을 둔다.
- 이미지가 많은 슬라이드는 설명을 줄이고, 중요한 callout 2-3개만 유지한다.

### 4. 디자인 고도화

- Style A를 기준으로 고정한다.
- 모든 슬라이드는 1920x1080 fixed stage를 유지한다.
- 한 슬라이드에 표, 코드, 다이어그램, 긴 bullet을 동시에 넣지 않는다. 밀도가 높으면 슬라이드를 분리한다.
- 각 섹션 첫 장은 짧은 선언형 문장과 큰 시각 요소로 구분한다.
- 기술 설명 슬라이드는 "왼쪽 핵심 문장 + 오른쪽 근거 이미지/다이어그램" 또는 "상단 흐름 + 하단 근거" 중 하나로 통일한다.

### 5. QA 고도화

- Playwright로 전체 슬라이드 카운트, 이미지 로드, overflow, 1280x720 및 모바일 viewport 스크린샷을 확인한다.
- 대표 슬라이드는 실제 스크린샷을 열어 사람이 읽을 수 있는지 확인한다.
- PDF export 전에는 로컬 HTML 기준으로 먼저 QA를 통과한다.
- 발표 직전에는 speaker script와 slide map의 제목/순서가 실제 HTML과 맞는지 확인한다.

## 고도화 때 사용할 스킬/도구

- `frontend-slides`: 최종 HTML 발표자료 구조, fixed 16:9 stage, Style A 확장, 슬라이드 QA 기준에 사용한다.
- `pdf`: 기존 PDF와 최종 PDF를 렌더링해 페이지 단위로 비교하고, export 결과의 잘림 여부를 확인할 때 사용한다.
- `imagegen`: 확보하지 못한 사진형 리소스나 배경성 비주얼을 임시 생성할 때 사용한다. 아키텍처/ERD처럼 정확성이 필요한 도식은 우선 HTML/SVG 또는 Figma/Mermaid로 만든다.
- `node_repl` + Playwright: 로컬 `presentation.html`을 열어 스크린샷 QA, 이미지 로드 검사, overflow 검사를 자동화한다.
- `figma-generate-diagram` / `figma-use`: 아키텍처, ERD, sequence diagram을 별도 편집 가능한 산출물로 만들 필요가 있을 때 사용한다. 단, HTML 안에서 직접 재현 가능한 경우에는 덱 내부 SVG/HTML 도식이 더 단순하다.
- `presentations`: HTML이 아니라 PPTX/Google Slides 변환 또는 재구성이 필요해질 때만 사용한다.
- Git/GitHub 도구: 단계별 커밋, 외부 저장소 dev 브랜치 근거 확인, 사용자 GitHub 업로드 준비에 사용한다.

## 권장 작업 순서

1. 현 상태 커밋 확인
2. `09_final-slide-map.md`를 고도화용 구조로 정리
3. 리소스별 사용처를 `asset-map.md`에 다시 매핑
4. 아키텍처, ERD, callback/WebSocket sequence를 다시 그릴지 결정
5. `output/presentation.html`을 Style A 기준으로 개편
6. speaker script를 실제 슬라이드 흐름에 맞게 갱신
7. Playwright 스크린샷 QA
8. 필요한 경우 PDF export QA
9. 최종 커밋

## 커밋 전략

- 고도화 전략/기준 문서 변경: 별도 커밋
- 슬라이드 맵 구조 변경: 별도 커밋
- 리소스 정리 및 다이어그램 교체: 별도 커밋
- HTML 덱 개편: 별도 커밋
- QA 수정 및 export 산출물: 별도 커밋

이 방식이면 프로토타입, 구조 변경, 디자인 고도화, QA 수정의 책임이 커밋 단위로 분리된다.
