# 우수주의보 15분 발표 스크립트

목표 시간: 14분 30초 내외. 각 슬라이드는 평균 25~30초, 기술 핵심 슬라이드는 40~50초로 설명한다.

## 1. 표지

안녕하세요. 저희 팀 우수주의보는 이미지와 센서 기반으로 빗물받이 상태를 판단하고, 그 결과를 관리 화면에 반영하는 프로젝트입니다. 발표에서는 문제 정의부터 AI 분석, DB와 서버 흐름, WebSocket 화면 갱신까지 구현 중심으로 설명드리겠습니다.

## 2. 프로젝트 한 줄 요약 + 전체 흐름 도식

우수주의보의 핵심은 입력부터 화면 반영까지의 흐름을 끊기지 않게 연결하는 것입니다. 이미지와 센서 입력이 있고, scheduler가 분석 작업을 만들면 Backend가 AI 서버에 요청합니다. AI 서버 결과는 callback으로 돌아오고, DB에 저장된 뒤 WebSocket event를 통해 대시보드와 상세 화면 갱신으로 이어집니다.

## 3. 팀 구성과 역할

역할은 네 축으로 나누었습니다. 송희수 팀원은 YOLO와 OpenCV, 라벨링, AI pipeline을 맡았습니다. 이명근 팀원은 Backend, DB 연동, callback 저장, WebSocket 처리 구조를 맡았습니다. 오택률 팀원은 Frontend, 인프라, Jenkins CI/CD를 맡았습니다. 김윤섭 팀원은 발표 구성, XGBoost 학습 기준, AI 서버와 Backend 통신 구조 설계를 맡았습니다.

## 4. 목차

발표는 다섯 부분입니다. 먼저 개발 필요성과 기존 방식 검토를 보고, 다음으로 AI 분석 설계, 웹 서버와 서비스 구축, 인프라 구성, 마지막 기대효과와 Q&A로 마무리하겠습니다.

## 5. 전체 기술 스택/구성 + 전체 아키텍처 요약

전체 구성은 Frontend, Backend, AI, DB, Infra로 나누어집니다. Frontend는 Next.js와 React 기반이고, Backend는 FastAPI와 SQLAlchemy, DB는 PostgreSQL입니다. AI는 YOLO, OpenCV, XGBoost를 조합했고, Docker, Nginx, Jenkins로 실행과 배포 흐름을 구성했습니다.

## 6. 도시 침수와 빗물받이

빗물받이는 도로 위 빗물이 배수관으로 들어가는 첫 지점입니다. 이곳이 낙엽이나 쓰레기로 막히면 강우 중 배수 흐름이 제한됩니다. 그래서 우수주의보는 개별 빗물받이 상태를 확인하고, 위험 시설을 우선 파악하는 흐름에 집중했습니다.

## 7. 강우 중 상태 변화

강우 중에는 상태가 빠르게 변합니다. 비가 오면 이물질이 유입되고, 막힌비율이 올라가며, 수위가 상승하고 유속이 떨어질 수 있습니다. 이 변화는 정기 점검 시점과 다를 수 있기 때문에 현재 상태를 반영하는 판단 흐름이 필요합니다.

## 8. 기존 점검 방식의 한계

기존 점검과 청소는 유지관리에서 꼭 필요합니다. 다만 강우 중 동시다발적으로 바뀌는 상태를 빠르게 판단하기에는 시간차가 있습니다. 시민 신고도 중요하지만, 신고가 들어오기 전의 개별 시설 위험도를 정리하기에는 한계가 있습니다.

## 9. 기존 방식/사례 검토 ① 점검·신고

첫 번째로 정기 점검과 시민 신고를 봤습니다. 정기 점검은 관리 기준을 만드는 데 강점이 있고, 시민 신고는 현장 발견에 강점이 있습니다. 다만 두 방식 모두 강우 중 상태 변화나 시설별 우선순위를 자동으로 계산하는 데에는 제한이 있습니다.

## 10. 기존 방식/사례 검토 ② QR·센서·관제

두 번째로 QR, 센서, 관제 방식입니다. QR과 관리번호는 위치 특정과 이력 연결에 좋고, 센서는 수위나 유속 같은 수치 상태를 볼 수 있습니다. 관제는 여러 지점을 모아보는 데 유리합니다. 우수주의보는 여기에 이미지 근거와 AI 판단, 화면 반영 흐름을 더하는 방향입니다.

## 11. 우수주의보 차별점

우수주의보는 이미지와 센서값을 함께 사용합니다. 개별 빗물받이 단위로 상태를 판단하고, 판단 근거를 DB에 남긴 뒤 대시보드와 상세 화면에 반영합니다. 신고를 대체하는 서비스가 아니라, 점검 우선순위와 상태 확인을 보조하는 구조입니다.

## 12. 참고 자료/정책/사례 기반 목표

기능 목표는 기존 관리·신고 체계를 참고해 설정했습니다. 정확한 근거가 없는 비용이나 수치는 넣지 않았고, 개별 빗물받이 상태 판단, 근거 저장, 화면 반영이라는 구현 가능한 흐름에 집중했습니다.

## 13. 일정표

진행은 기획과 설계, AI 분석 설계, Backend와 DB 구현, Frontend 구현, 통합과 시연 준비 순서로 진행했습니다. 발표의 뒤쪽 기술 흐름도 이 순서와 거의 동일하게 따라갑니다.

## 14. AI 분석 설계 개요: YOLO + OpenCV

AI 분석은 YOLO와 OpenCV를 같이 사용합니다. YOLO는 이미지에서 보이는 객체나 영역을 탐지하는 데 유용합니다. OpenCV는 전처리와 실제 막힌 영역 해석을 보조합니다. 두 결과를 합쳐 막힌비율 판단으로 연결했습니다.

## 15. 막힌비율 판단 구조

막힌비율은 단일 모델 출력만으로 정하지 않았습니다. YOLO가 배수구와 이물질 후보를 찾고, OpenCV가 mask 처리와 어두운 영역 보정, obstruction area estimation을 보조합니다. 이 결과를 같이 사용해 최종 막힌비율을 계산합니다.

## 16. XGBoost 입력과 위험도 분류

XGBoost에는 막힌비율, 탐지 신뢰도, 수위, 유속을 입력 기준으로 사용했습니다. 출력은 양호, 주의, 위험, 판단불가입니다. 여기서 최종 위험 점수는 실제 침수 확률이 아니라 우수주의보 내부 분류를 위한 계산 점수입니다.

## 17. 결과/검증

결과 판단은 이미지와 센서 둘 중 하나만 보지 않습니다. 막힌비율과 탐지 신뢰도로 영상 막힘 점수를 계산하고, 수위와 유속으로 센서 정체 점수를 계산합니다. 최종 위험 점수는 영상 45%, 센서 45%, 수위 10%를 반영합니다. 근거가 부족하면 판단불가로 두고, 반대로 YOLO 분석이 실패해도 센서가 명확히 위험하면 위험으로 분류합니다.

## 18. 서비스 구축 개요

서비스 흐름은 scheduler, Backend, AI 서버, PostgreSQL, WebSocket으로 구성됩니다. 중요한 점은 Frontend가 분석을 직접 요청하는 구조가 아니라는 것입니다. scheduler가 작업을 만들고 Backend가 AI 서버에 요청하며, 결과는 callback으로 돌아옵니다.

## 19. 관리자 대시보드 흐름

관리자 대시보드는 전체 상태를 빠르게 보는 화면입니다. 지도, 위험 시설 목록, 선택 시설 정보를 통해 어떤 시설을 먼저 확인해야 하는지 볼 수 있습니다. WebSocket event가 오면 최신 데이터를 다시 조회해 화면을 갱신합니다.

## 20. 상세 화면 흐름

상세 화면에서는 시설별 판단 근거를 보여줍니다. 이미지 분석 결과, 센서 추이, AI 결과, 과거 이력을 같이 보여주어 왜 이 시설이 해당 상태로 분류됐는지 확인할 수 있게 했습니다.

## 21. DB 설계 / ERD

DB는 callback과 WebSocket보다 먼저 이해해야 하는 부분입니다. drains, sensor_data, yolo_results, xgboost_results, analysis_jobs가 연결됩니다. 분석 작업은 어떤 센서값과 이미지 분석 결과, 최종 분류 결과를 연결하는 중심 역할을 합니다.

## 22. 센서 데이터 복합키 설계

센서 데이터는 특정 빗물받이의 특정 측정 시점을 함께 식별해야 합니다. 하나의 빗물받이는 여러 시계열 데이터를 갖기 때문에 drain id와 measured time 조합을 설계 기준으로 두면 어떤 센서값이 분석에 쓰였는지 명확해집니다.

## 23. 스케줄러 기반 비동기 분석 작업 생성

분석 작업은 scheduler 기반으로 생성됩니다. 우기 운영을 가정하면 10분 주기로 작업을 만들 수 있고, Backend는 생성된 작업을 기준으로 AI 서버에 분석 요청을 보냅니다. 이렇게 화면 응답과 분석 처리를 분리했습니다.

## 24. callback 저장

AI 서버가 분석을 마치면 Backend callback으로 결과를 전달합니다. Backend는 YOLO/OpenCV 결과와 XGBoost 최종 결과를 나누어 저장하고, 작업 상태도 함께 갱신합니다. 중복 callback 가능성도 저장 기준에서 고려합니다.

## 25. WebSocket 갱신

WebSocket은 모든 데이터를 직접 전달하는 통로라기보다 화면 갱신 trigger입니다. Backend가 result persistence 이후 event를 보내면 Frontend가 event를 받고 최신 데이터를 다시 조회해 대시보드와 상세 화면을 갱신합니다.

## 26. 전체 서비스 흐름 요약

전체 흐름을 다시 묶으면 scheduler가 작업을 만들고, Backend가 AI 서버에 요청하고, AI 분석 결과가 callback으로 돌아오고, DB에 저장되며, WebSocket event로 화면 갱신이 시작됩니다. 이 흐름이 우수주의보의 핵심 구현 흐름입니다.

## 27. 시스템 아키텍처

시스템은 Browser, Nginx, Frontend, Backend, AI server, PostgreSQL로 나누어 볼 수 있습니다. Nginx는 진입점과 routing을 맡고, Backend와 AI 서버는 분석 요청과 결과 저장 책임을 분리합니다.

## 28. Docker / Nginx / Jenkins CI/CD

Docker는 실행 환경과 배포 단위를 맞추는 역할을 했고, Nginx는 request routing과 entry point 구성을 맡았습니다. Jenkins는 GitHub 변경 이후 build와 deploy 흐름을 자동화하는 CI/CD 구현에 사용했습니다.

## 29. 향후 RTSP, MQTT, 알림 확장

현재 구현과 향후 확장은 분리해서 봐야 합니다. RTSP CCTV, MQTT 기반 실제 센서, 알림과 리포트는 현재 구현이라고 주장하지 않고 future work로 둡니다. 현재 구조는 이 확장을 받을 수 있는 흐름을 먼저 구성한 단계입니다.

## 30. 기대효과

기대효과는 네 가지입니다. 시설별 상태 확인, 위험 시설 우선순위 확인, 이미지·센서·AI 판단 근거 확인, 분석 결과 저장과 화면 반영 흐름 확인입니다. 이를 통해 점검 전 어떤 시설을 먼저 볼지 판단하는 데 도움을 줄 수 있습니다.
